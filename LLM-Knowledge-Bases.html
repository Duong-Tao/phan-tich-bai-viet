LLM Knowledge Bases

Something I’m finding very useful recently: using LLMs to build personal knowledge bases for various topics of research interest. In this way, a large fraction of my recent token throughput is going less into manipulating code, and more into manipulating knowledge (stored as markdown and images). The latest LLMs are quite good at it. So:

Thu thập dữ liệu và giao diện làm việc

Data ingest:

I index source documents (articles, papers, repos, datasets, images, etc.) into a raw/ directory, then I use an LLM to incrementally “compile” a wiki, which is just a collection of .md files in a directory structure. The wiki includes summaries of all the data in raw/, backlinks, and then it categorizes data into concepts, writes articles for them, and links them all. To convert web articles into .md files I like to use the Obsidian Web Clipper extension, and then I also use a hotkey to download all the related images to local so that my LLM can easily reference them.

IDE:

I use Obsidian as the IDE “frontend” where I can view the raw data, the the compiled wiki, and the derived visualizations. Important to note that the LLM writes and maintains all of the data of the wiki, I rarely touch it directly. I’ve played with a few Obsidian plugins to render and view data in other ways (e.g. Marp for slides).

Đặt câu hỏi và xuất kết quả

Q&A:

Where things get interesting is that once your wiki is big enough (e.g. mine on some recent research is ~100 articles and ~400K words), you can ask your LLM agent all kinds of complex questions against the wiki, and it will go off, research the answers, etc. I thought I had to reach for fancy RAG, but the LLM has been pretty good about auto-maintaining index files and brief summaries of all the documents and it reads all the important related data fairly easily at this ~small scale.

Output:

Instead of getting answers in text/terminal, I like to have it render markdown files for me, or slide shows (Marp format), or matplotlib images, all of which I then view again in Obsidian. You can imagine many other visual output formats depending on the query. Often, I end up “filing” the outputs back into the wiki to enhance it for further queries. So my own explorations and queries always “add up” in the knowledge base.

Bảo trì, mở rộng và hướng phát triển

Linting:

I’ve run some LLM “health checks” over the wiki to e.g. find inconsistent data, impute missing data (with web searchers), find interesting connections for new article candidates, etc., to incrementally clean up the wiki and enhance its overall data integrity. The LLMs are quite good at suggesting further questions to ask and look into.

Extra tools:

I find myself developing additional tools to process the data, e.g. I vibe coded a small and naive search engine over the wiki, which I both use directly (in a web ui), but more often I want to hand it off to an LLM via CLI as a tool for larger queries.

Further explorations:

As the repo grows, the natural desire is to also think about synthetic data generation + finetuning to have your LLM “know” the data in its weights instead of just context windows.

TLDR: raw data from a given number of sources is collected, then compiled by an LLM into a .md wiki, then operated on by various CLIs by the LLM to do Q&A and to incrementally enhance the wiki, and all of it viewable in Obsidian. You rarely ever write or edit the wiki manually, it’s the domain of the LLM. I think there is room here for an incredible new product instead of a hacky collection of scripts.

🔍 Phân tích bài viết

📌 Tóm tắt ý chính

Karpathy mô tả một hệ thống quản lý tri thức cá nhân: thu thập raw documents → LLM tự động biên dịch thành wiki Markdown có backlinks, categorize concepts/entities → dùng Obsidian xem trực quan → query phức tạp qua LLM agent. Điểm mấu chốt: LLM điều hành wiki, người chỉ supervise. Không cần RAG phức tạp vì wiki 100 articles/400K từ đủ mức độ cho Q&A tự động.

🗺️ Mindmap

Xem chi tiết trong LLM Knowledge Bases.canvas (JSON Canvas format).

Các bước luân hồi:

  • Ingest: raw documents → Local indexing
  • Compile: Auto-generated wiki (concepts, entities, backlinks)
  • Query: LLM agent tìm kiếm xuyên wiki, trả lời với synthesis
  • Enhance: Đầu ra (slide, ảnh, markdown) store lại vào wiki → loop tiếp

💡 Insight & Góc nhìn đa chiều

  1. Paradigm shift khỏi RAG: Thay vì vector DB + retrieval, Karpathy tin rằng LLM đã đủ khả năng “auto-maintain” index file + context window ở scale nhỏ (100–400K từ). Điều này phá vỡ assumption rằng RAG là obligatory cho mọi trường hợp.

  2. LLM-as-developer: Workflow này giao cho LLM toàn quyền viết, organise, maintain knowledge structure. Con người chỉ supervise. Đây là bước tiến từ “AI hỗ trợ” → “AI chính là developer/curator”.

  3. Compounding knowledge: Output từ Q&A được “file lại” vào wiki → tăng mass của wiki → Q&A tiếp theo có context richer → chain reaction. Đây là vòng lặp positive feedback hiếm gặp trong knowledge work.

  4. Obsidian làm visual glue: Không phải Obsidian là centerpiece, mà là transparent frontend cho một data layer mà LLM quản lý. Người dùng thấy markdown/slides nhưng phía sau là LLM-driven logic.

  5. Tool ecosystem vẫn cần: “Hacky collection of scripts” + CLI tools vẫn là thành phần. Karpathy thừa nhận không còn “elegant” lắm, nhưng functional. Có cơ hội cho product startup ở đây.

⚖️ Phản biện

  1. Scalability claim chưa chứng minh: Karpathy nói “pretty good at auto-maintaining index at this ~small scale” (100 articles). Nhưng nếu scale lên 10K articles + millions từ thì sao? Context window sẽ bị overflow, retrieval có thể bị ngẫu nhiên. Không rõ threshold thực tế.

  2. Quality degradation ẩn: Mỗi lần LLM compile wiki, có hallucination. Mỗi lần query nó tóm tắt, mất nuance. Không giải quyết cumulative error problem—10 lớp abstraction sẽ dẫn distortion đáng kể.

  3. Obsidian lock-in: Workflow phụ thuộc sâu vào Obsidian ecosystem + plugins (Marp, v.v.). Nếu switch tools = rewrite toàn bộ pipeline. Không portable.

  4. Người dùng passive quá: “Rarely edit wiki manually” có vẻ tiện lợi nhưng cũng dễ bias—LLM tự organize thì bias theo training data nó, không phải domain expert. Supervision nhẹ có thể miss critical errors.

  5. Cost bị downplay: Mỗi query xuyên wiki là API call có cost. 100 articles/400K từ × N queries/day × token pricing = non-trivial infrastructure cost. Bài không nhắc tới cost angle.

❓ Câu hỏi mở

  1. Khi nào RAG thực sự cần thiết? Karpathy nói không cần, nhưng có scenario nào (patent search, compliance, high-stakes domain) mà RAG lại superior? Hay là personal KB scale của anh vừa nằm trong “sweet spot” không cần RAG?

  2. Synthetic data + finetuning có thực hiện được không? Karpathy mention ở cuối: “synthetic data generation + finetuning để LLM biết data trong weights”. Nhưng fine-tune trên KB của riêng anh = model sẽ overfit, lose generalization. Trade-off nào đó?

  3. Làm sao detect hallucination tích lũy? Sau 10 lần compile/query/store-back cycles, wiki có bị drift? Có linting tool nào detect “content corruption”?

🇻🇳 Liên hệ Việt Nam

  1. Ứng dụng ngành gia công kim loại: một công ty Nhật có rất nhiều design documents, manufacturing specs, quality standards. Thay vì người mới phải đọc hết manual cũ kĩ, có thể:

    • Collect tất cả PDF specs → Web Clipper chuyển Markdown
    • LLM auto-generate wiki “Design Knowledge Base”
    • Người mới query “What are the tolerance specs for aluminum gears?” → LLM tìm từ specs documents
    • Tăng onboarding speed & reduce rework từ specification misunderstanding

  2. Thị trường labour: Hiện tại, “subject matter expert” (người hiểu deep design + quality rules) rất khan hiếm ở VN, salary cao. Nếu wiki này được manage tốt, junior engineer có thể:

    • Access curated knowledge của expert
    • Reduce context-switching cost
    • Tăng productivity → lower per-unit cost

    Điều này có thể làm giảm salary gap giữa senior/junior, vì knowledge base bổ sung cho expertise mà không có.

  3. Supply chain visibility: Nhiều công ty VN (plastic, garment, metal) chưa có unified knowledge system về supplier specs, quality metrics, cost history. Karpathy’s approach có thể:

    • Index supplier documents từ many sources (Excel, Email, PDF)
    • LLM query “Which suppliers meet ISO9001 + low lead time?” → instant answer
    • Reduce procurement time, better negotiation data

📖 Giải thích thuật ngữ

  • RAG (Retrieval-Augmented Generation): Kỹ thuật nối vector database với LLM. User query → search vectors tương tự → feed context vào LLM → generate answer. Dùng khi dataset quá lớn để fit context window.

    Ví dụ: Nếu company có 100,000 pages documentation, không thể load hết vào ChatGPT (overflow). Dùng RAG: user query → search top-K relevant pages → feed K pages vào LLM.

  • Backlinks: Link từ page A → page B được ghi ở page B là “B has backlink từ A”. Obsidian auto-maintain. Dùng để see cross-reference, build knowledge graph.

    Ví dụ: Page “Aluminum Alloys” có backlinks từ “Aircraft Design”, “Automotive Parts”, “Corrosion Prevention” → thấy concept này relate đến ba domain.

  • Synthetic data generation: Dùng LLM gen fake data based on pattern của real data. Dùng để augment training set hoặc test robustness.

    Ví dụ: Nếu có 100 design specs, dùng LLM gen 1000 variations (slightly different tolerances, materials) để fine-tune model.

  • Context window: Số token LLM có thể process one-shot. ChatGPT-4o: ~128K tokens (~100K words). Limit này constraint “how much wiki can fit in single query”.

  • Obsidian: Note-taking app hỗ trợ wiki-style linking (wikilinks), markdown, plugins. Free + powerful. Dùng để view/navigate Markdown files locally.
